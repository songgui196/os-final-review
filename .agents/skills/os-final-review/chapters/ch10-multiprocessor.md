# 第 10 章 多处理机操作系统

**位置：** 书 p.312–339 / PDF 333–360。**层级：** 全书备查；同步与调度的扩展。

## 核心框架：硬件拓扑决定共享代价

多处理机通过多个 CPU 并行工作提升整体能力，但调度、同步和共享存储争用也更复杂。区分紧耦合共享存储系统与其他并行/分布式组织，再问谁共享内存、谁运行内核、谁决定调度。增加处理机数量不能自动消除串行部分和同步开销。

| 概念（§10.1–10.3） | 判断依据 | 影响 |
|---|---|---|
| UMA | 访问共享内存的成本基本统一 | 统一抽象易管理，但互连、总线和内存可成为争用点 |
| NUMA | 远近节点的内存访问成本不同 | 线程与其数据的放置和亲和性影响实际性能 |
| 主从式 OS | 主 CPU 运行内核管理，从 CPU 接受分派 | 实现集中；主处理机易成瓶颈或故障点 |
| 独立监督式 OS | 各 CPU 有其管理程序与资源 | 管理相对独立，协作和全局信息处理需额外机制 |
| 对称式 OS | 处理机较对等地参与 OS 与任务运行 | 并行服务好，但内核共享状态要正确同步 |

## 同步（§10.4）：把等待成本也算进去

- **集中式 vs 分布式同步**：控制信息由集中管理者维护，或分布在多节点/参与者间。后者减少单点集中但通信协议更复杂。
- **自旋锁**：对短临界区且持锁者能在其他 CPU 上推进的场景，可能比阻塞/唤醒轻；长等待时一直测试会浪费 CPU 和共享互连。单核只关本核中断不能替代多核锁。
- **读—复制—更新（RCU）**：读者尽量轻量，写者构造新版本并发布，在已有读者不再可能使用旧对象后回收。发布新指针不等于可以立刻释放旧数据。
- **二进制指数补偿、待锁 CPU 队列**：减少密集重试或有序安排等待者，改善大量 CPU 争同一锁的开销；公平和吞吐需权衡。
- **定序、面包房、令牌环**：依序号或令牌确定进入资格；面包房算法用取号与顺序比较协调，令牌环靠唯一令牌授予进入权。故障、令牌丢失和顺序维护需要协议支持。

## 调度（§10.5）：同时想数量和位置

**自调度**用公共就绪队列供空闲 CPU 取任务，简单、负载容易平衡，但相关线程不一定同时获得 CPU。**成组调度**让合作线程一组运行，减少互等；**专用处理机分配**在应用执行期间保留 CPU，减少切换但可能浪费；**动态调度**按运行情况调整分配数量，更灵活也更复杂。固定/动态进程分配、亲和性和迁移成本要一起考虑。

多 CPU 或分布式等待也可死锁：检测时需要适当的全局或协同信息，不能只因某 CPU 的本地队列无进展就判断整个系统死锁。

## 演练（自拟）

两个合作线程 T1、T2 持续交换数据，T1 在节点 A，数据页也在 A，T2 被移到 B。可能一方面增加并行，另一方面增加远程内存/缓存一致性通信；应比较吞吐、迁移开销和数据亲和性。若频繁互相等，成组调度可减少对方未被调度带来的空等；若长时间等 I/O，专用 CPU 则可能闲置。
